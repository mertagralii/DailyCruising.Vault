1. **Diver capacity tied to rental type, not boat** — same boat carries different diver counts for day vs. night tours; prevents over-promising
2. **Night range is soft constraint** — if not configured, system uses legacy behavior (backwards compatible)
3. **All server limits exposed from API** — single source of truth prevents server/frontend internal consistency divergence
4. **Authorization centralized** — one permission check point across all 11 new endpoints rather than duplicating logic
5. **Enforcement both-layer** — night range applied in both application and database; application-only would be bypassable via SQL
6. **Diver flag logic** — no code checks rental type name; flag travels with catalog entry and frontend respects it unconditionally
7. **Diver capacity hidden from customer pages** — field would imply guarantee when enforcement is incomplete; shown on platform forms as reference
8. **Update endpoints do full replacement, not merge** — documented in contract (`b681aee`); prevents silent data loss when fields are absent
